# Guest agent: установка, диагностика и восстановление

Для каждой принадлежащей QCL виртуальной машины QEMU устанавливается и включается
QEMU Guest Agent. В NixOS используется `services.qemuGuest.enable`; транспорт
`org.qemu.guest_agent.0` должен быть предоставлен гипервизором. Для иного backend
проверяется соответствующий поддерживаемый механизм гостевой интеграции.
Объявленная настройка образа не доказывает исправность уже работающей VM.

## Приёмка и выбор канала

После установки, первого запуска и плановой перезагрузки отдельно проверить:

1. Наличие пакета, действительного исполняемого файла и устройства канала в госте.
2. Состояние VM, подключение канала и состояние службы агента.
3. Успешный обычный `guest-ping` через штатный клиент гипервизора.
4. Выполнение короткой read-only команды и получение её завершённого статуса.

Успешный ping не доказывает работоспособность всех команд, NFS, Slurm или solver.
Работающий процесс также не доказывает сходимость и научную приёмку.

Для компактных проверок служб, ресурсов и состояния работ предпочитать guest
agent, если он доступен. Использовать известные абсолютные пути команд или
заранее проверять PATH: отсутствие `squeue` в окружении агента не означает
отсутствия Slurm. Для длительной команды сохранять identity операции и PID
сразу после отправки, затем получать статус этого PID. После потери соединения
сначала сверять прежний receipt и фактический процесс; не запускать повторный
reader, build или mutation вслепую. Таймаут клиента сам по себе не отменяет
запущенную гостевую команду. Вывод и объём чтения ограничиваются потребностью
конкретной проверки и фактическими ресурсами.

Крупные финальные артефакты передавать проверенным файловым потоком с проверкой
размера и целостности; упаковка массивов в JSON/base64 агента для этого обычно
не подходит. Права на сохранение результата определяет поручение пользователя.
История и checkpoint не становятся финальным результатом из-за похожего имени.

## Если агент не отвечает

Сначала установить владельца VM и операции, затем различить следующие случаи:

| Наблюдение | Следующая проверка |
| --- | --- |
| VM выключена или приостановлена | Проверить actual status гипервизора и причину; не запускать её без применимого разрешения |
| Нет устройства канала | Сверить конфигурацию гипервизора и устройство в госте |
| Служба отсутствует или упала | Проверить установленный пакет, executable, unit и журнал через доступный независимый канал |
| VM и служба работают, ping зависает | Проверить активных клиентов канала, предыдущие RPC и состояние протокола |
| Ping проходит, отдельная команда не завершается | Проверить поддержку команды, guest PID, PATH, её ресурсы и фактический результат |

Сообщение Proxmox «guest agent is not running» может скрывать исключение или
таймаут ping. Оно само по себе не устанавливает, что процесс агента остановлен.
Независимая сетевая доступность гостя подтверждает лишь часть его работоспособности.

## Восстановление синхронизации протокола

[Протокол QEMU](https://www.qemu.org/docs/master/interop/qemu-ga-ref.html#command-guest-sync-delimited)
предусматривает `guest-sync-delimited` при новом подключении и после клиентского
таймаута. Перед запросом отправляется байт `0xFF`, сбрасывающий частично прочитанный
JSON в агенте. Клиент отбрасывает старые ответы до ответа с собственным уникальным
целочисленным маркером; входящий `0xFF` сбрасывает состояние его собственного parser.
Обычный ping без такой синхронизации может продолжать зависать на незавершённом
сообщении предыдущего соединения.

Для принадлежащей QCL VM восстановление проводит один владелец операции:

1. Сохранить ограниченный operational receipt: VM/boot identity, версии клиента
   и агента, время, прежние RPC/PID и наблюдаемую ошибку; без научных массивов.
2. Сверить, что другой клиент или lifecycle-операция не использует канал, и
   выяснить исход предыдущей команды. Неизвестный исход mutation не исправляется
   повторной отправкой. Проверка отсутствия клиента сама по себе не является
   межпроцессной блокировкой: на время операции исключить новые обращения.
3. Через соответствующий протокол клиентской реализации выполнить синхронизацию
   с `0xFF` и уникальным маркером. Не смешивать параллельные подключения и чужие
   ответы. При неустановленном исключительном владении остановиться до записи.
4. После получения именно своего маркера закрыть соединение и проверить обычный
   ping, затем отдельную короткую read-only команду штатным клиентом гипервизора.
5. Сохранить результат или неопределённость. Повторная попытка требует сверки
   фактического исхода; отсутствие ответа не доказывает отсутствие эффекта.

Это порядок диагностики для оператора, а не установленный автоматический watchdog.
Не перезагружать VM и не перезапускать службы только из-за общей ошибки клиента.
Патч общего пакета Proxmox затрагивает и чужие VM: он требует отдельной оценки
области действия и проверки, а не изменения ради одной QCL VM.

## Подтверждённый случай 2026-10-30

На двух QCL гостях службы агента продолжали работать, а обычные ping не получали
ответа. VM оставались запущены, диски не сообщали I/O error, сетевой канал гостя
отвечал. В установленном клиенте `qemu-server 9.2.8` запрос синхронизации отправлялся
без ведущего `0xFF`; агент в госте имел версию `10.2.4`.

Контрольная смена только протокольного префикса восстановила ответы, после чего
обычные ping и асинхронные read-only команды завершились. Перезапуска агента,
служб и VM не было. Это подтверждает объяснение с незавершённым состоянием JSON;
какое именно прежнее сообщение и когда оборвалось, не установлено. Случай не
доказывает такую причину для всех ошибок guest agent или её наличие в иных версиях.
Первичные operational receipts хранятся в частном журнале исполнения; чужие VM
и научные данные в проверку восстановления не входили.
